# V01 T1 — two stores in one persistent CloudKit container

Status: native configuration rejection observed on 2026-10-23. T2 was not
launched because T1 failed before a data save could complete. This result
elaborates the [V01 procedure](../graphevo-2-v01-procedure.md), after the successful
[T0 cross-device control](v01-t0-2026-10-23.md).

## Question and exact configuration

Can one `NSPersistentCloudKitContainer` mirror two separately routed SQLite
stores using the same model, iCloud container identifier, and `.private` scope?

The experiment used two new file paths, A.sqlite and B.sqlite, under a new run
namespace. Both descriptions used the same optional-attribute `V01ProbeItem`
model, no model configuration partition, asynchronous loading, history tracking,
and remote-change notifications. Each description received its own
`NSPersistentCloudKitContainerOptions` instance, with the same dedicated test
container identifier and `.private` database scope.

Planned inserts explicitly assigned the A fixture to store A and the B fixture
to store B; snapshots used `affectedStores` for the selected physical store and
only the runID predicate. An independent iPad reader would open one fresh store
and fetch the entire run without a graph-label filter. The native rejection
prevented those planned data operations from being exercised on hardware.

Do not confuse an `NSPersistentCloudKitContainer` object with the provisioned
CloudKit container named by its options. T1 used one of the former and one of
the latter. Two separate persistent-container objects using the same cloud
container are a different, unexecuted experiment.

## Native result

The app launched directly into the T1 writer. The framework raised an uncaught
`NSInvalidArgumentException` with this reason:

> Cannot assign the same iCloud Container Identifier to multiple persistent stores with the same database scope.

The process terminated with signal 6. This is an Objective-C exception, not an
`Error` delivered through a store-loading callback or caught by Swift
`async throws`. The initial report had already been retained, but remained
`Running; not completed evidence`, with no finished timestamp and
`localSaveCompleted = false`. Its empty errors array is not evidence of success;
the native console exception and termination establish the configuration failure.

No completed T1 save, per-store snapshot, or export was observed. T2 was not
started, and no fallback, scope substitution, custom zone injection, or alternative
container topology was attempted to make the requested configuration pass.

The laboratory should reject the now-known duplicate cloud-container/scope
mapping before invoking the native API on subsequent runs, recording a preflight
rejection distinctly from this observed native exception. That protective check
is not another framework experiment or a workaround that provides isolation.

## Implication and next question

The exact single-persistent-container configuration tested here is rejected on
the tested platform. We therefore have no observed separate or mixed cloud
replicas from T1/T2. This result neither proves nor disproves R01 under every
supported architecture.

A possible next experiment would use two independent
`NSPersistentCloudKitContainer` objects, each owning a different SQLite store,
with the same cloud container and private scope. That would test a different
ownership topology and must preserve the rule against multiple mirror owners
for the same local SQLite file. Its cloud separation and fresh-peer behavior
remain unverified; no v2 architecture has been selected from this result.
